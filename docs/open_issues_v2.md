### 甲　在当前 layout 上，智能体几乎从来没有可以表达偏好的选择

> **2026-09-05 更新：根因已定位并修复，量级大幅改善，但门槛判定仍未做。**
> 根因不是地图缺选择，是候选生成器写成了"策略"（判断局面 → 只返回该局面的动作），
> 被当成"菜单"用却从未重写。修复后（13 009 个状态、容忍度 1 步）：
> 有 ≥2 个真动作可选的决策点从 **0（0.0%）** 升到 **6 331（48.7%）**，
> 动作组合从 0 种增至 4 种，最常见的是 `GET_ONION vs GET_TOMATO`（5 892 次）。
> H0 经影子重放验证不变（0/13 009）。
> **2026-09-05 再更新**：H0 重测完成（60 局），每局有真选择的决策点 193.8 个（最少 149），建议门槛「每局 ≥ 60、≥ 3 种组合」，**通过，不换地图**。门槛数值待用户确认。
> 下文保留原始诊断，作为改动前的基线记录。

这是整个项目的头号风险，v1 把它拆成了六条（#3/#4/#5/#27/#28 加矩阵 M3-3），显得像六个中等问题。它是一个问题。

**证据**（会话 `20260813_145715`，891 步，可用 `matched_replay` 复现）：

```
可行候选集大小：         {1: 459, 2: 396, 3: 36}
在任务最优处并列的候选：  {1: 891}      ← 891 步全部无并列
含两个以上非等待候选：    仅 {GET_DISH, GET_TOMATO}: 36 步（4.0%）
```

推论：**容忍度为 0 时，可接受集在全部 891 步都只有一项。**机制只有在放开容忍度之后才有东西可重排。

放开到 `--step-tolerance 1` 之后：

```
可接受集大小：{1: 785, 2: 100, 3: 6}
其中：WAIT@5 + WAIT_NEAR_POT@15 ............... 83
     PUT_DOWN_OBJECT@5 + PUT_TOMATO_IN_POT@80 .. 17
```

也就是说，**在实际使用的容忍度下，唯一那对真动作竞争（GET_DISH vs GET_TOMATO）一次都没进过可接受集。**能重排的几乎全是"等这儿还是等锅边"。

真动作竞争实际有两对，不是一对（v1 写错了）：

```
PUT_TOMATO_IN_POT@80 vs PUT_DOWN_OBJECT@5   305/891 步
GET_DISH@60          vs GET_TOMATO@50        38/891 步
```

`PUT_DOWN_OBJECT` 不是等待类（`task_cost.py:213`，且 `test_task_cost.py:98` 有断言），所以 v1 那句"其余竞争的一方都是等待类"对 305 步是假的。

**缺的东西：一个数字门槛。**做完 M1 / M2（下面的候选生成器改动）之后，凭什么判断"够了"？现在没有任何依据。建议在动手之前先写死，例如：

> 每位参与者的一次条件中，可接受集 ≥ 2 且其中至少两项为非等待候选的决策点，须不少于 N 个；
> 且这些决策点覆盖不少于 K 种不同的子目标对。

N 与 K 由 M2-10 需要的样本量反推（见 E6）。

**fallback 的代价必须写明。**若补救后仍不达标，就要改 layout 或配方 —— 那会作废：冻结题库、127 个仿真会话、`Hu_general`、`hierarchical_hu_runtime.md` §3.1 的整条 `task_cost` 标定曲线，以及 Linguistic 分支自己的 `probe_states.json`。**这是重启，不是"更大的改动"。**
