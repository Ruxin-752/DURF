## 1. 主线机制

### #1　Ours 是会话后离线更新，Linguistic 是会话内在线更新
**现象**　`durf/group_a/play_with_baseline.py:831`，Hu 模型在 episode 循环开始前一次性加载，中途从不重载。Ours 的成对标签在会话结束后才产生。Linguistic 实时写 `feedback_updates.jsonl`。
**影响**　任何"同一局内反馈前后行为是否变化"的口径都会让 Ours 恒为 0，差异全部来自更新时机而非学习能力。M1-2 门槛也只对 Linguistic 生效。
**决定**　改成和 Linguistic 一样的实时更新。
**状态**　未开始。**前置 C。**

### #2　检查点存档不存在
**现象**　运行时不落盘 F0 / F5 / F10 / F15 的模型快照。
**影响**　M2-7（学习曲线）与 M2-10（同点重放）都以此为输入。M2-10 的工具已实现且验证通过，但目前没有"反馈前 / 反馈后"两个检查点可读。
**状态**　未开始。**前置 C**，依赖 #1。

### #3　`next_needed_ingredient` 把"先拿哪个食材"折叠成了一个选项
**现象**　返回 `best_missing[0]`，只给一个食材。32000 步里 26440 步受影响；其中约 83% 的步骤存在真实的"番茄还是洋葱"选择，但候选池里只出现一个。
**影响**　偏好最该发挥作用的那类决策根本没进候选集。
**计划**　新增 `GET_ONION` 候选、任务分 65（低于 `GET_TOMATO` 的 70）。H0 的选择不变（仍选 70 那个），但"先拿哪个"进入候选池，容忍度一放开就能被偏好重排。
**状态**　已设计，未实施。**属前置 B。**
**注**　先前"此改动可解锁 PC-T03 / PC-T10 两道探针"的理由已作废 —— 那两道题随 20 道 participant_elicited 题一并删除了。改动的理由现在只剩"让真动作竞争存在"，这个理由本身成立。

### #4　`teammate_holding` 直接删掉 GET_DISH 候选
**现象**　`if not teammate_holding(state, player_index, "dish")` 使 1080 步中 GET_DISH@60 根本不生成。
**影响**　这是 gate/value 分离原则的第三处违反 —— "伙伴不应决定某个选项是否存在，只应影响它值多少分"。前两处（候选存在性、路径选择）已修。
**代价**　与前两处不同，**移除它会改变 H0 在这些状态下的实际动作**，属于"改变赢家"的高代价改动，需要完整的影子重放验证。
**状态**　未决定。**属前置 B。**

### #5　整个 layout 只有一个决策点存在两个真动作竞争
**现象**　`GET_DISH` 60 与 `GET_TOMATO` 50。其余决策点要么只有一个可行候选，要么竞争的一方是等待类。
**影响**　这是最根本的一条：**我们最想研究的"真动作竞争"在当前 layout 上几乎不存在。**#3 与 #4 都是针对它的补救。若补救后仍不足，需要考虑改 layout 或改配方，那是更大的改动。
**状态**　未解决，#3 / #4 是当前的应对。**属前置 B。**

### #6　任务分里的 2 / 10 / 15 / 20 是回填出来的
**现象**　这几个值是在"容忍度 0 必须复现被退休的 `recovery_action_override`"这一约束下反推的，不是独立设计的。原始分数体系（100 / 95 / 90 / 80 / 70 / 60 / 50 / 5 / 0）是规则教师的优先级编码，本身也是无量纲的。
**影响**　任何以任务分为单位的阈值都缺乏可辩护的依据。步数容忍度（`--hu-step-tolerance`）绕开了这个问题，但等待类候选的分值仍留在这套编码里。
**状态**　已知，未处理。优先级低于 #3 / #5。

### #7　`hu_general` 任务头是流水线缺陷的产物，必须重训
**现象**　冻结的 `hu_general` 任务头是在标签流水线修复之前训练的。
**影响**　任何用它得到的结论都不可用。
**状态**　未开始。依赖 #3 / #4 定稿后再训，否则要训两次。

### #8　全部仿真任务性能数字作废
**现象**　H0 基线被协作死锁削弱了约 4 倍（单局回报 60 → 240–260，`cf9349c` 修复）。
**影响**　所有以旧 H0 为参照的对比、标定表、非劣性讨论全部失效。
**状态**　待重跑。**前置 A。**

### #9　评估层全部未入 git
**现象**　`durf/evaluation/`、`data/evaluation/`、`scripts/generate_evaluation_matrix_docx.py`、各 docx 均为未跟踪状态。
**影响**　"冻结版评估协议"目前没有任何东西在兑现；无法追溯改动。
**状态**　按用户决定暂缓。权威版本混乱问题已解决：唯一权威文件为 `docs/DURF_Evaluation_Matrix.docx`，旧的 v1.2 与 v2.0 已移入 `_deprecated_pre_experiment_elicitation/`。

### #10　`common_probe_scores.jsonl` 全项目只读不写
**现象**　`common_evaluation.py:435` 读它，`validate_probe_set.py` 与多份文档引用它，**没有任何地方产生它**。
**影响**　M2-1 / M2-3 / M2-4 / M2-5 / M2-6 / M2-7 / M2-9 / M3-1 全部悬空。现有代码回退到读 `probe_hits.jsonl`，但那是运行时按帧记录、彼此序列相关的诊断数据，矩阵明文禁止计入样本量。
**状态**　未实现。需要一个离线打分器：三个模型在同一题面与候选集上打分并落盘。

### #11　M2-4 当前零可用样本
**现象**　共识层 13 题中 10 题为对照题，判断题仅 3 题；且全部题项的 `h0_selected` 与 `discriminative` 字段仍为 `null`。
**影响**　判别性子集准确率算不出来。
**补题指标**（已与校验器对齐）　题项总数 18–40；判断题 ≥ 8；协作层题项 ≥ 8（现为 3）；对照题 ≥ 总数 30%；H0 标注后判别性题项 ≥ 判断题的 60%。
**状态**　待 H0 重测后标注 + 补题。**前置 A。**补题由研究者写定，不涉及参与者，不与实验前问卷的废止冲突。

### #12　运行时探针对三组读出完全相同的数
**现象**　ε-satisficing 改造后 `final_score == task_score`，而 `common_evaluation.py` 读的正是 `final_score`。
**实测（全仓 132 个 `probe_hits.jsonl`）**　`final_score == task_score` 的候选 **114 392 个，不相等的 0 个**（另有 1 588 个缺字段）；`hu_score ≠ 0` 的候选只有 **173 / 115 980（0.15%）**。也就是说，现有全部落盘数据里，这个读数**几乎处处等于 H0 的任务分**。
**影响**　M2 的核心读数丧失区分度。
**状态**　**矩阵已改**（v2.1 两段式：可达性 + 可接受集内排序），**代码未改**。`common_evaluation.py` 需按两段式重写，并要求落盘 `task_score` / `hu_score` / `acceptable_set_hit` 三个字段。

### #13　M2-2 有 78% 的记录靠并列裁决
**现象**　Ours 29/37 条由"归因记录原始次序 → 字典序"的确定性裁决决定首选项；Linguistic 是真正的唯一最大值。
**影响**　并列率相差如此之大时单独比较 M2-2，会把"归因粒度粗"误读为"判定准确"。
**状态**　矩阵已要求与 M2-8 强制并列报告。归因粒度本身是否要改，未决定。

### #14　M1-2 门槛只对 Linguistic 生效
**状态**　依赖 #1。改成在线更新后自动对称。矩阵已加适用性说明。

### #15　M1-3 更新时延无产出方
**现象**　两组均未落盘时延字段。
**状态**　未实现。矩阵要求未落盘时报告为缺失、不得以 0 代替。

### #16　公平性审计查错了对象
**现象**　前置门槛比对 `subgoal_executor`（运行时从未被调用），却不比对 `hu_task_tolerance` / `hu_coordination_tolerance` —— 后者才是决定整个效应大小的旋钮。
**状态**　**矩阵已改**（v2.1 已换成容忍度参数 + 候选生成器版本），**代码未改**：一致性比对逻辑需同步。

### #17　M3-1 不读轨迹
**现象**　现有实现复用探针命中记录中的候选排序，而非 `trajectory.jsonl` 里实际执行的子目标。
**影响**　测得的仍是模型排序而非落地行为，与 M2-3 近乎同义反复，M3 这一层实际上不存在。
**状态**　矩阵已写明正确做法与分母（可接受集 ≥ 2），代码未改。分母定义**前置 B**。

### #18　M3-2 算的不是文档写的量
**现象**　实现算的是"非首条负面反馈占全部负面反馈的比例"（反馈条数占比），文档定义的是"同一 issue 再次收到负面反馈的条件概率"；且从未读取 `total_step` 或时间戳，间隔步数恒为缺失。
**状态**　矩阵已给出正确计算式，代码未改。另有一个未解决的更深问题：未按"问题再次出现的机会数"归一化 —— 某 issue 后续根本没有再出现的机会时，其未复发不构成改进证据。

### #19　T2 未实现，且现有定义方向是反的
**现象**　无产出方。且若按"该步未执行有效动作即为空闲"计算，会把因避让队友而产生的 `stay` 记为空闲 —— **协作更好的智能体反而被判为更不流畅**。
**状态**　矩阵已加"协作性等待单独成栏、不计入空闲"的判定规则，代码未实现。

### #20　T1 曾塌成一个数
**现象**　`mean_episode_steps` 因固定时限 800 恒等；`task_success_rate` 恒为 1.0；`episode_reward` 与 `positive_reward_events` 完全共线。
**状态**　**已在 v2.1 处理**：主结局只取 `episode_reward`，其余三项剔除并写明理由。

### #21　非劣性边界不存在，且两张标定表符号矛盾
**现象**　全项目没有任何地方定义等效界限 Δ。文档里两张标定表对差值的符号还不一致：修复前 20 vs 60（我们输），修复后 280 vs 260（我们赢）。
**状态**　矩阵已冻结**设定规则**（Δ = H0 重测后单局回报均值的固定比例，比例值须在数据收集开始前写定），旧标定表已作废。**数值待前置 A。**

### #22　U1–U5 读的问卷 schema 不存在
**现象**　`_load_questionnaire` 里没有矩阵描述的那套字段。
**状态**　未修。属"现在就能补完、与主线无关"的一类。

### #23　分析单位规定按被试，代码是 pooled 且无被试字段
**现象**　标准化输出没有 `participant_id`，按会话合并计算，文档写的"所有比率型指标先按参与者计算"根本执行不了。
**状态**　矩阵已加硬性实现要求，代码未改。

### #24　M2-6 旧定义在 2 候选集上代数退化
**现象**　旧的归一化偏好位次在只有两个候选时代数上等于 `pairwise_accuracy + 0.5 × tie_rate`，不是独立信息。
**状态**　**已在 v2.1 重定义**（可接受集内部按 `hu_score` 排位，并要求同时报告可接受集大小），代码未改。

### #25　H0 当熟悉局会把练习效应混入 T1
**现象**　参与者在熟悉局时尚不熟练，其后各条件的任务表现天然更高。
**状态**　矩阵已加警示与两个处理方案（另设一个位于正式条件之后的 H0 局，或在报告中声明该差值为练习效应与方法效应的合计）。协议尚未定稿。

### #26　U5 删除后，偏好漂移无工具
**现象**　U5 以实验前偏好问卷的两次施测为工具，该问卷已随实验前偏好征集一并废止。
**状态**　已删除。若仍要考察"与自适应智能体协作后偏好是否漂移"，须另设一份不向参与者提示研究维度的事后工具。未开始。
