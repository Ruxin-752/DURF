## 一、这个项目在做什么

一句话：

> **让人用日常语言告诉 AI 队友"我希望你怎么配合"，AI 就真的照着改。**

场景是 Overcooked（双人做菜游戏）。人和 AI 一起做番茄番茄洋葱汤，人可以随时打字说"你别老抢我要拿的盘子"，系统把这句话变成一条可训练的偏好，AI 之后的选择就应该不一样。

要证明的命题分四段，缺一段都不成立：

```
① 话被听懂了  →  ② 变成了正确的偏好  →  ③ 偏好改变了行为  →  ④ 菜没做砸
```

对照的是一个已发表方法（Learning Rewards from Linguistic Feedback），两边接同一个底座 agent，比谁更有效。

## 二、三个角色

| 角色 | 是什么 | 谁写的 |
|---|---|---|
| **底座 agent** | 会做菜的基本能力：规则打分选目标 + 运动规划器走路 | 本项目 |
| **Ours** | 事件归因 + 条件化偏好模型 Hu | 本项目（要发表的贡献） |
| **Linguistic** | 语言 → MDP 特征 → 贝叶斯奖励权重 | 改编自 Sumers et al. AAAI 2021 |

三者共用同一个底座，都只做一件事：**给候选行为重新打分**。谁都不改环境奖励，谁都不直接输出低层动作。

这句话描述的是最初的通用框架，Linguistic 和 Ours 的 coordination 层现在仍然这样做：

```
final_score = task_score(底座给的) + λ × method_score(方法给的)
然后取最高分
```

但 Ours 的 **task 层**已经不是这样了（2026-09-03 起）：`task_score` 和 `method_score`
量纲不同、不该相加，现在改成 ε-约束分层满足式——先在任务分的容忍带内筛出可接受候选，
再让偏好模型只在这个子集里排序。细节见 §四 和 `docs/hierarchical_hu_runtime.md` §3。

## 四、Ours 的机制：四层

```
        游戏状态 + 近期轨迹
                │
   ┌────────────▼────────────┐
   │ L1  候选生成             │  规则级联，产出"现在可以做什么"
   │     ✅ 空手/持物分支均已修 │  队友挡路不再直接删候选（闸门/价值分离）；
   │     （2026-09-03）        │  持物分支已放开为多候选，见坑①
   └────────────┬────────────┘
                │ 候选 subgoal + task_score
   用户说的话 ──▼────────────┐
   │ L2  语义归因（已建成）    │  轨迹 → 候选事件 → LLM 选事件 → 成对偏好标签
   └────────────┬────────────┘
                │
   ┌────────────▼────────────┐
   │ L3  偏好模型 Hu（已建成） │  task 头：Hu_general + condition_delta（默认无 user_bias）
   │                          │  coordination 头：Hu_general + user_bias + condition_delta
   └────────────┬────────────┘
                │
   ┌────────────▼────────────┐
   │ L4  决策执行（已建成）    │  task：ε-约束满足式（不加权相加）；coordination：仍是
   │                          │  task_score/prior + λ·Hu 的加法 → 冲突处理 → 动作
   └─────────────────────────┘
```

### L2 语义归因：这是真正跑通的贡献

设计原则很干净：**LLM 放在事实抽取之后，不许它发明事实**。

1. 程序先从轨迹里检测出 **14 类候选事件**（"AI 挡了人的路"、"AI 反复捡起又放下"、"AI 没趁人等待时备料"…）
2. 把「用户这句话 + 最近 25 步轨迹 + 候选事件列表」发给 **DeepSeek**
3. LLM 只能**从候选里选**一个事件，选完还要说明在什么条件下成立、AI 该更倾向哪个 subgoal
4. 回来的结果做硬校验：选的事件不在候选里就作废、时间窗口强制覆写成事件的真实窗口、LLM 挂了就退回规则版

产物就是 Hu 的训练样本：**在这些条件下，应该优先 A 而不是 B**。

### L3 Hu：是线性模型，不是神经网络

这点很多人会误解。Hu 的完整形式是：

```
score(用户, 条件, subgoal)
  = 全局偏置[subgoal]
  + 用户偏置[用户, subgoal]
  + Σ 条件权重[条件k, subgoal] × 条件值k        (条件 True=+1, False=−1, 未知=0)
```

- **参数量**：task 头 330 个、coordination 头 32 个。就这么大。
- **损失**：成对排序的 logistic loss，逐样本 SGD，200 轮、lr 0.05
- **两个头完全独立**：task（11 个 subgoal，28 个条件）和 coordination（2 个选项 YIELD/CONTINUE，14 个条件）。因为"去拿番茄"和"让个路"没法比较

**个体化的三级分解（2026-09-03 起，两个头不再对称）**：

```
task 头：        Hu_user = Hu_general(冻结) + condition_delta[条件, subgoal]
coordination 头： Hu_user = Hu_general(冻结) + user_bias[subgoal] + condition_delta[条件, subgoal]
```

task 头默认不再有 `user_bias` 这一项（`PerUserAdapter.enable_task_bias=False`），原因见下方
新增的结论段落。这是可逆开关，不是删除。

**最强的一条实验结论**：只用 30 条训练样本做消融——

| | task 准确率 | coordination 准确率 |
|---|---|---|
| Hu_general | 1.000 | 0.713 |
| + user_bias | 1.000 | 0.713（**一点没变**） |
| + condition_delta | 1.000 | **0.966** |

**个体化的价值 100% 来自 condition_delta，user_bias 单独毫无作用。** 这条最初是当作
"支撑三级架构"的证据写下的，但后来跨四个 persona 重新核对发现：这句话对 task 域和
coordination 域的含义完全不同。task 域的 `user_bias`（无条件地偏好某个子目标）四个 persona
全部落在 ±0.06 以内，是噪声，不是"没测出信号"，而是这个概念本身在 task 域就站不住——
"要不要拿番茄"天然是情境决定的，没有脱离情境的固定偏好。coordination 域的 `user_bias`
则学到了有意义、随 persona 单调变化的值（cooperative 0.05 → lenient 0.14 → polite 1.00 →
selfish 1.74，和"越自私越不愿让路"的直觉吻合）——只是它单独（不配合 condition_delta）不足以
翻转任何测试集决策，这也是上表"+user_bias 一点没变"的真正原因。基于这条更精细的证据，
`PerUserAdapter` 现在 task 头结构性去掉 `user_bias`，coordination 头保留。

⚠️ **但 Hu_general 是从模拟人格来的**：4 个 persona 的 4515 条样本，只保留跨人格方向一致的 3806 条。所以"通用人类先验"这个说法必须限定成"4 个人格模板的共同部分"，上面这条关于 `user_bias` 的结论也是。

## 五、Linguistic 对照方法：一句话进来发生什么

改编自论文，53 维手工特征，两条并列路线：

**Route 1（论文原版，无需训练）**

```
"You're blocking my path, please move away."
  → 按标点切成短语
  → 三类分类器：这是评价 / 命令 / 描述？（决定归因到轨迹、动作还是特征）
  → 五类细分：指的是轨迹 / 特征 / 空间动作 / 行为模式 / 其他？
  → 落到 53 维特征上：{blocks_human_path:1, human_wait_cost:1, ...}
  → VADER 情感分析给极性
  → 高斯共轭更新奖励权重 w（先验 N(0, 25I)）
  → 用新的 w 重新给所有候选 subgoal 打分
```

**Route 2（神经网络，已训练）**：文本 + 轨迹特征 → 网络直接预测完整 53 维权重 → 逐维高斯更新。十折交叉验证，冻结测试集准确率 99.99%。

这个 baseline 做得相当扎实：三份文档逐条对齐论文、四道置信度闸门、更新幅度用 KL 约束、模型冻结带 SHA256 校验、测试集一次性打开机制。

⚠️ **它自己诚实标注的边界**：Route 2 只用文本（不看轨迹）就能达到 99.92%，说明这个合成任务主要靠显式语义，**没有真正做到时间归因**；真人风格探针只测了 4 条中的 1 条；三类分类器在真人确认的 89 条上只有 **64%** 准确率。

## 六、实验怎么做

**被试内设计，每人 50–60 分钟，全程英语打字反馈。**

| 步骤 | 时长 | 干什么 |
|---|---|---|
| 1. 同意 + 前测 | 5 min | 填游戏经验、英语水平 |
| 2. 教学 | 5 min | 练习地图，不算数据 |
| 3. **H0 评估** | 6 min | 和不个体化的 AI 玩，**不给反馈** |
| 4. **方法 A 适应** | ≤12 min | 边玩边给约 15 条反馈，**每条即时更新模型** |
| 5. 方法 A 冻结评估 | 6 min | 加载 model_F15，不再学习 |
| 6. 休息 | 3–5 min | 重置回初始模型 |
| 7–8. 方法 B | 同 4–5 | 换另一种方法 |
| 9. 最终比较 | 5 min | 二选一"你更想和谁再玩一局"+ 理由 |

- **A/B 顺序在参与者间平衡**，H0 固定最前；两个方法只以 **Agent A / Agent B** 呈现，参与者不知道哪个是研究者自己的
- **反馈配额**：每方法目标 15 条、上限 20 条。**不允许因为某方法转化率低就多给它反馈**——转化率本身就是结果
- **Checkpoint F0/F5/F10/F15**：按**累计原始反馈条数**存快照（不是按成功更新数，否则转化率高的方法会被更晚评测，输入不对等），用来画学习曲线
- **人工复核**：pilot 阶段可以用，**正式实验参与者不参与**；gold 标签由两名研究者事后独立标注，只用于评价，不能回头修正在线学的标签

**地图**：10×6 环形单格宽走廊，两人无法错身，只能有人退开或绕整圈。锅在上中、盘子机左上、番茄机左下、洋葱机下中、出餐口在右。**这个"过不去"的物理设定是整个协作偏好研究的前提。**

## 七、评估：三侧框架

按导师的框架重组，两个实验组各测三侧：

| 侧 | 指标族 | 测什么 |
|---|---|---|
| **AI 侧** | M1 反馈处理 | 15 条话里方法真正用上了几条 |
| | M2 反馈解释 + 偏好学习 | 理解对不对；排序改没改对 |
| | M3 行为落地 | 排序变化有没有进入实际动作 |
| **人侧** | U1–U4 主观体验 | 采纳意愿 / 智能感知 / 协作感知 / 共情感知 |
| **共同侧** | T1 任务能力、T2 协作流畅度 | 菜没做砸；配合更顺畅 |

人侧用成熟量表：UTAUT 行为意向、Godspeed 感知智能、Hoffman 协作流畅度、PETS 共情（待预实验确认）。

**两条读法上的硬规矩**：
1. **判别性题项准确率**（只在底座会答错的题上算）和**对照题项准确率**（只在底座会答对的题上算）**必须成对报告**。前者升后者降 = 模型退化成"一味顺从"，算失败不算成功。
2. **分差（margin）禁止跨方法比较**——两边的分数量纲不同，而且调大 λ 就能放大分差却不改变任何排序。

## 九、五个最要紧的坑

### ① 候选池经常只有一个选项 —— 最致命

`generate_candidate_subgoals` 是一棵**带提前 return 的规则级联**：手里拿着任何东西，就直接返回唯一那个动作。

实测 800 步的 session：

```
手里拿着东西    候选数 1    442 步   ← 100%，无一例外
空手           候选数 1     14 步
空手           候选数 2    294 步
空手           候选数 3     50 步
```

**持物占 55% 的时间，候选恒为 1。** Hu 是个重排序器，一个候选没得排。

后果：12 条已归因的偏好里，**只有 2 条**在反馈之后出现过可检验的相似情景，全局共 7 次机会。而人最想表达偏好的时刻恰恰都在持物分支——"你拿着番茄的时候先让我过去"、"端着汤别急着送，等我先过"——**全都表达不出来**。

根因是：这个函数原本是**规则教师**（为蒸馏低层执行器生成监督标签），教师只需要输出一个正确答案。后来 Hu 直接复用了它的内部列表当动作空间。设计文档写了"Hu 只在已有候选中重排序"，但**从没规定候选生成器必须满足什么**，于是退化成单点而无人报警。

好消息：**放开候选可以做到对基线零行为影响**——只要新候选的 task_score 严格低于原有那个，容忍带为 0 时选择结果完全不变。所以不用重新验证任务底座。详见 `docs/mechanism_blueprint_v1.md`。

✅ **进度（2026-09-03）**：队友挡路直接删候选的问题已经修——候选存废现在只受"物理上能不能到达"这一个客观条件影响，队友位置改成只影响路线，绕不开才退化成"无视队友"的路线并标记供审计（`route_blocked_by_partner`）。**持物分支的候选生成也已放开**：5 个持物状态从单一 `return` 改成 2–4 个带 task_score 的候选，原本压在候选生成之外的 `recovery_action_override` 两个强制触发器（`AI_HELD_DISH_BEFORE_SOUP_READY` / `AI_HELD_UNNEEDED_INGREDIENT`）随之退休。16000 步影子重放（4 人格 × 10 seed × 400 步）验证 `hu_task_tolerance=0` 时动作与退休前逐步一致，0 处偏差。**本坑最致命的那部分已经解决**；候选集是否真的让 Hu 学到的偏好在持物场景里生效，仍需 P2 的 sim 回归验证。

### ② λ 的量纲从没标定过 —— task 层已修复

task 层 `task_score` 是 0–100，相邻候选差 10–30 分；而 Hu 分数量级只有 ±10。λ=1 时 **Hu 在 task 层几乎不可能翻转决策**。coordination 层的 base 是 0/1，Hu 轻易主导。

数据佐证：task 探针 3037 次里只有 **3 次**符号翻转（0.1%）；coordination 112 次里翻转 **38 次**（34%）。

**这解释了为什么所有个体化效果都只出现在 coordination 域。**

✅ **进度（2026-09-03）**：task 层的量纲问题已经从根上解决——不再把 `task_score` 和
`hu_score` 相加，改成 ε-约束分层满足式：`hu_score` 只在任务分的容忍带内挑选，容忍带宽度
`hu_task_tolerance` 单位是任务点数，不再需要给两个不可通约的量找一个共同的权重。
~~**coordination 层还没有改**，仍然是 prior + λ·Hu 的加法，这条坑对 coordination 域原样成立。~~
✅ **coordination 层也改了（2026-09-04）**：prior 满足、Hu 只排序、不相加，λ 删除；prior 只有
两档，所以 `--hu-coordination-tolerance` 是一个 0/1 开关。改的时候发现 CONTINUE 没有上界
（YIELD 有承诺期 + 冷却，坚持没有），偏好一旦选坚持就是永久迎面死锁（整局 0 分），已给
CONTINUE 加上对称的冷却。见 `docs/hierarchical_hu_runtime.md` §3。

✅ **进度（2026-09-04）**：容忍带的单位进一步从"任务点数"换成"估计的额外步数"
（`--hu-step-tolerance`，`task_cost.py`），排序仍是冻结底座、容忍带 0 零变化。仿真里第一次
拿到一条可标定的曲线：与 H0 相反的人格在 3/8/≥10 步预算下分别翻转 12/21/120 个决策点，
与 H0 一致的人格纹丝不动，分数不降。过程中修掉两个规则层面的洞：等待类候选会把逐决策容忍
带撑成无界（一整局 0 分），以及 Hu 随机初始化让没标注过的 subgoal 带着随机意见（放下/捡起
死循环）。细节见 `docs/hierarchical_hu_runtime.md` §3.1。

### ③ 训好的低层执行器在运行时从未被调用 —— 已下线

`train_subgoal_executor.py` 训出了一个 CNN（val 准确率 0.9994），但运行时代码里有一段白名单：候选生成器能产出的全部 9 个 subgoal 都直接返回运动规划器的动作，**只有落在白名单外才会调 keras 模型**——而白名单已经覆盖全部。

所以：**所有实验里 AI 的动作都来自运动规划器，那个神经网络是死代码**。但 README、设计文档、session metadata 都把底座描述成 `state → subgoal → learned low-level executor action`。**"learned"这一环在部署中是空的**，论文里必须说清楚。

✅ **进度（2026-09-03）**：已经正式下线，不再是"文档说 learned、代码里其实没用"的静默不一致——`play_with_baseline.py` 和 `sim_session.py` 现在都无条件走运动规划器，keras 模型默认不加载（两边都有 `--load-retired-executor` 标志，仅用于回归对比时手动加载），底座描述改成 `state → subgoal → planner action`，和实际代码一致。这次核查还发现 `sim_session.py` 此前遗漏了这次下线——仍然无条件加载模型、保留一段永远不会命中的白名单调用分支——已经补齐一致。Ours 和 Linguistic 两个方法都是这样，底座claim不再有"learned"这个空环节。

### ④ 评估的 probe 主指标已被自己证伪

在真实 session 上实跑，报表显示 `probe_pairwise_accuracy = 1.0`，但拆开看：

- 177 条记录里只有 **31 条（17.5%）**真能判对错
- 其中 **27 条（87%）**来自同一个探针
- 该 session **575 个候选的 hu_score 全部为 0**——这个"偏好学习准确率"完全来自底座规则，**H0 考同一份卷子也是 1.0**
- coordination 域可评 **0 条**

修复方案（人工出题、候选集写死的冻结题库，33 题）已经写好，但**关键的两步还没做**：33 题的 `feasibility_verified`（模拟器可行性）和 `h0_selected`（H0 打分）**全是 null**。不做完就往下跑，会得到"三个 1.0"的无意义表格。

## 十二、名词速查

| 名词 | 人话 |
|---|---|
| **subgoal** | 高层动作意图，如"去拿番茄""放进锅""让路"。共 13 个（11 任务 + 2 协作） |
| **condition** | 描述当前局面的布尔特征，如"锅在煮""人拿着盘子""走廊很窄"。共 28 个 |
| **candidate event** | 程序从轨迹里检测出的"发生了什么"，如"AI 挡了人的路"。共 14 类 |
| **pairwise label** | 一条训练样本：在这些条件下，应该优先 A 而不是 B |
| **Hu** | 偏好模型的名字。线性模型，不是神经网络 |
| **Hu_general** | 所有人共享的偏好先验，冻结不动 |
| **condition_delta** | 个体化的核心：这个人在特定条件下的特殊偏好 |
| **probe** | 考题。给模型一个固定局面问它选什么，用来测学没学会 |
| **checkpoint F0/F5/F10/F15** | 收到第 0/5/10/15 条反馈时的模型快照，用来画学习曲线 |
| **λ (lambda)** | coordination 层仍在用的偏好分数权重，λ=0 就是完全不个体化；task 层已经不用 λ，改用 `hu_task_tolerance`（见下） |
| **hu_task_tolerance** | task 层的容忍带宽度，单位是任务点数：愿意为学到的偏好放弃多少任务分，=0 就是完全不个体化 |
| **YIELD / CONTINUE** | 协作域仅有的两个选项：让路 / 继续走自己的。这是 Hu 能看到、能选的全部词表 |
| **WAIT / BACK_OFF / REROUTE** | `YIELD` 选中之后"具体怎么让"的三种执行方式，由规则判断，不是 Hu 的选项：原地等 / 退到最远的空格 / 换一条绕开人的路。优先级 REROUTE > BACK_OFF > WAIT，记录在决策的 `reason` 字段里 |
